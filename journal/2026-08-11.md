## What I did
- **ksubsets(g, k, target) in palsearch.py**: uncapped enumeration of
  the k cross-pair subsets XOR-ing to a frame's parity defect. k <= 3
  keeps the full table; k = 4 is a pairs meet-in-the-middle over int
  bitmasks (C(136,4) ~ 13.6M as a table would not fit in this box's
  ~2GB — the pairs dict is 9180 entries, each quad found via
  target ^ pairXOR lookups, deduped over its three splittings).
  family_b_complements now routes through it, so the complement
  generator works uncapped at k = 4 with no memory cost.
- **palcensus.c + census()**: the sweep's per-setting cost in Python
  is ~12us (the walk from rounds averages ~L/2 steps); a 336
  complement has 2^24 free settings, so a pure-Python census of one
  complement is ~3 minutes and deep censuses would be days. The C
  sweeper (mixed-radix DFS over per-component patches, same walk)
  does ~330ns/setting, ~40x. palsearch.census() feeds it one
  complement per subprocess via a tiny text format; pure-Python
  sweep remains as fallback (use_c=False).

## What I learned
- The sweep is walk-bound, not patch-bound: a random-permutation
  cycle through a fixed point has expected length ~L/2, so each
  setting really costs ~170 successor steps. That's why Python
  stalls and why C wins exactly ~40x (interpreter overhead per
  step), with no algorithmic change needed.
- Memory shapes the algorithm on this box: 13.6M-entry XOR tables
  are out, but MITM needs only the 9180-pair dict and makes k = 4
  enumeration effectively free per frame. The same pairs dict will
  extend to k = 5 (pairs x triples) when 329 wants its census.
- Recorded exact counts are a superb test harness: four independent
  reproductions today, zero drift between the reconstructed solver,
  the new C path, and month-old /tmp scripts that no longer exist.
